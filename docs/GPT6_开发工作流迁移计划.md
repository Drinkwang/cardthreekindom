## 模型使用分工

以下强度是本项目的候选设置，不是已证明的最优参数。

| 工作 | 推荐设置 | 使用条件 |
| --- | --- | --- |
| 日常修复、GDScript 开发、单页面迭代 | GPT-6.1 Sol / medium | 默认承担开发、验证和交付 |
| 跨战斗、养成、装备、城建的功能 | GPT-6.1 Sol / high | medium 在对照任务中遗漏关键关系时提高强度 |
| 难复现问题、存档迁移、复杂架构决策 | GPT-6 Astra / medium，必要时比较 high | Sol 经诊断和验证后仍未通过，或该类任务评测表明 Astra 明显更可靠 |
| 已定内容的文档整理、明确的小改动 | GPT-6 Luna / high | 任务边界和验收结果清楚；先通过试用再纳入 |

先迁移到 Sol，再逐步验证其他模型的适用范围。模型变更、推理强度变更和提示词改写分别评测，以便判断改善来自哪里。

## 对照评测任务与验收

各模型使用相同起始快照、任务文字、资源和工具；保存每次改动与日志。先以 5 个任务筛选，再把反复出现的问题纳入日常检查。

| 代表任务 | 应观察的结果 |
| --- | --- |
| 只读解释装备、带兵与携带位的互斥关系 | 结论能指向真实代码，不臆造接口或规则 |
| 修复一个实际存在的桌面或抽屉布局问题 | 三尺寸截图可读；6/9/15 张牌场景符合要求；输入仍可用 |
| 修复一个实际存在的轻重拍边界问题 | 耐力、一次手势命中、结算时机符合当前任务约定；玩法自检通过 |
| 检查或修复一个存档兼容问题 | 旧档、测试档、离线结算和归属关系有明确验证；玩家正式档不受验证过程影响 |
| 从 v1.3 策划拆出一个主桌实施任务 | 范围、依赖与验收具体；目标设计没有被说成已实现 |

若不存在适合修复的真实缺陷，选择已知历史缺陷，在隔离副本中重现，或改为只读诊断；不为测试模型改坏正式工程。

验收以两套自检、相关交互和任务专用检查为准。`SelfTest` 当前调用无参数 `quit()`，所以不能仅凭进程退出码认定通过，还必须读取“失败项 0”并检查错误日志；`PrintTest` 则同时检查失败计数和退出码。界面检查复用 [Screenshot 场景](D:/Pro/cardthreekindom/tests/Screenshot.tscn)。

候选模型必须满足功能和验证要求，之后再比较完成耗时、人工纠正次数及客户端可见用量。暂定采用门槛为连续 3 个真实任务通过；若关键任务失败，先诊断原因，再提高 Sol 强度或比较 Astra。没有本项目评测前，不承诺成本或速度下降比例；Codex 的计划用量也不能直接套用 API 单价。
